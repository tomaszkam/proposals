optional pointer accessor naming

1. Introduction

This paper suggest to rename optional pointer accessor from get_ptr (per P4189R0, accepted for C++29) to pointer.

2. Revision history

2.1. Revision 0

Initial revision.

3. Motivation

3.1. Local consistency

In author's opinion the pointer is more consistent with pre-existing optional API:

Operation Code
accessing contained object ("value") opt.value()
returning value or alternative opt.value_or(alt)
transforming value opt.transform(funct)
accessing pointer to contained object status-quo: opt.get_ptr()
proposed: opt.pointer()

The pointer name is already widely as the member name in the standard library. Most notably, containers and iterators use pointer member type to denote type of pointer used for object.

While the proposed name may seem inconsistent, especially given that C++23 made optional and range and view, the author believe that local consistency in naming is more important. Furthermore no other view from the standard provides a pointer member type.

3.2. Future extensions

One of possible and trivial extension of "accessing pointer to contained object or null", is an function that returns pointer to object or alternative pointer value, i.e. equivalent to: opt.has_value() ? opt.pointer() : alt_ptr. For optional of non-reference types, this eliminates a repeated check for presence of value inside pointer() function.

With proposed pointer name, the obvious name of such extension would be pointer_or, the current naming leads to get_ptr_or.

3.3. Alternative name: address

Possible alternative name would be address, as in "taking an address of containing object" in parallel to "getting an value of contained object.

Such approach would match naming to_address and addressof functions that produce pointer to an object. However the address name by itself is currently used as name of member that return cv void*, i.e. type that cannot be dereferenced:

  • coroutine_handle::address - the value is not connected to address of object returned from coroutine_handle::promise,
  • atomic_ref::address - accessing object via returned value may lead to data-races.

3.4. Rejected alternative: data

As previously mentioned, optional is continuous_range, and such ranges use data to expose address of the first element: either by having data member, or more generically via ranges::data.

At first glance, we could embrace the range API for optional, and rename the get_ptr to data. However, this would lead to change of the behavior or already supported ranges::data(opt): it will call opt.data() instead of to_address(opt.begin()).

While for non-empty optional opt, the behavior of opt.get_ptr() and to_address(opt.begin()) is equivalent, they result differs for empty optional:

  • opt.get_ptr() returns nullptr,
  • to_address(opt.begin()) can return any pointer for which +0 is well-formed.
In particular optional of non-reference type always return pointer to contained object (that is not within lifetime for empty optional).

4. Impact and Implementability

The proposed change has no-impact beyond the name of optional::get_ptr, and as simple rename does not cause additional implementability concerns.

5. Proposed Wording

The proposed wording changes refer to N5050 (C++ Working Draft, 2026-06-01).
