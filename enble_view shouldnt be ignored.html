enable_view shouldn't be ignored

1. Introduction

Addresses PL007: Define the extent member of the strided_slice

This paper proposes modification to the viewable_range concept, that prevents standard library facilities from implicitly forming a reference to the type that was explicitly designated to be an view (i.e. for which enable_view is true).

3. Motivation and Scope

The C++ views are subset of the ranges, that are inexpensive to move (and copy if supported), and consequently are stored by value when adapted by standard range adaptors, like views::transform or views::take. Such by-value semantics eliminate the risk of dangling-reference-related undefined behavior, when such view chain is returned:

  auto process_span(std::span<const int> s)
  {
    // span is a view and returned view chain stores a copy of
    // s parameter, and does not depend on its lifetime
    return s
      | std::views::transform([](int x) { return x * 3; })
      | std::views::take(20);
  }

  auto process_vec(const std::vector<int> v)
  {
    // vector is not a view by itself, and returned view chain
    // refers to it (ref_view is created), and dangles
    return v
      | std::views::transform([](int x) { return x * 3; })
      | std::views::take(20);
  }

As the difference between view and the range is mostly in semantic, the author of the range, must explicitly opt-in to it, by making sure that enable_view is true, by specializing it explicitly or deriving from either view_base or view_interface (see LWG3326: enable_view has false positives).

Given above, it seemis reasonable to assume, that once a type is designed as a view, it will always be stored by value in view chains. However, in cases when such type is not movable, library infrastructure will form a reference to such type when adapted.

3.1. Impact on std::optional

After the C++26 change that made it a view (P3168), std::optional may exhibit above behavior if the wrapped type is not movable, due to not being move-constructible, move-assignable, or both.

In particular move-assignability requirement, implies that lvalues optional, of const-qualifed types will be referenced (instead of stored by value) in view chain. For example when using std::optional<std::pair<const std::string, int>> (value type of std::map):

constexpr auto
process_rvalue()
{
  std::pair<const std::string, int> p("test", 20);
  return std::optional(p) | std::views::keys; // ill-formed
}

constexpr auto
process_lvalue()
{
  std::pair<const std::string, int> p("test", 20);
  std::optional opt(p);
  return opt | std::views::keys;
}

The changes proposed in this paper makes the operand of return in process_lvalue ill-formed.

3.2. Proposed fix: modify std::viewable_range

The ability of applying range adaptors, is controlled by the std::viewable_range, that is defined as follows:

template<class T>
concept viewable_range =
  range<T> &&
  ((view<remove_cvref_t<T>> && constructible_from<remove_cvref_t<T>, T>) ||
  (!view<remove_cvref_t<T>> &&
     (is_lvalue_reference_v<T> || (movable<remove_reference_t<T>> && !is-initializer-list<T>))))

The checks after confirming that type is range are split into three branches, corresponding to view::all:

  1. views are returned by value,
  2. non-views lvalues are wrapped into ref_view,
  3. non-views rvalues are wrapped into owning_view if they are movable.

However, as view<T> requires range<T> && movable<T> && enable_view<T>, type for which enable_view is true, but is not movable may end up in second branch (third branch requires movable).

This paper proposed changing to !view<remove_cvref_t<T>> to !enable_view<remove_cvref_t<T>>. Directly reflecting the intent of the class implementer, instead of silently ignoring it (possibly due error).

3.3. Impacts reaches up to C++20

While the paper focuses on examples using std::optional, the problem addressed by the paper can impact any user-defined range, for which enable_view is true, but it is not movable. Thus the issue is not limited to C++26, but C++20 and later standards.

4. Ship vehicle

Proposed changes should be implemented as DR, at least for C++26, and when possible to eariel standard. It is recommended that implementers approach above changes in similar manner as LWG issue would be.

5.1. Migration guide

As this paper make currently accepted code ill-formed, it can potentially lead to build failures and other breaking changes. This section list possible strategies of addressing them.

5.1.1. Correcting view implementation

As illustrated by the implementation experience from libstdc++, the changes in this paper may expose issue in the view implementation, that lead to them failing movable requirements. Correcting that will address the impact.

5.1.2. Explicitly use ref_view

While storing the reference to "view" may lead to dangling references, such uses are safe if the adapted view does not outlive the referenced object. In such cases, the changes proposed in this paper, will make code that was previously valid, ill-formed. For example:

 template<typename T>
   void process(std::optional<T> opt)
   {
     auto view = opt | std::views::transform(...) | ...;
     furtherProcessing(view);
   }

In such cases, the previous behavior may be explicitly restored by constructing ref_view explicitly. Either unconditionally:

 template<typename T>
   void process(std::optional<T> opt)
   {
     auto view = std::ranges::ref_view(opt) | views::transform(...) | ...;
     furtherProcessing(view);
   }

Or conditionally, to avoid any changes in the emitted code for movable, types:

 template<typename T>
   void process(std::optional<T> opt)
   {
     if constexpr (!std::movabile<T>)
     {
       auto view = std::ranges::ref_view(opt) | views::transform(...) | ...;
       furtherProcessing(view);
     }
     else
     {
       auto view = opt | std::views::transform(...) | ...;
       furtherProcessing(view);
     }
   }

5.1.3. Specialize enable_view conditionally

In situation when the user desires that they MyRange<T, Args...> is conditionally treated as view as previously, they can restore the previous behavior by providing enable_view specialization that is conditionally defined to true:

  template<typename T, typename... Args>
    constexpr bool enable_view<MyRange<T, Args...>> 
      = movable<MyRange<T, Args...>>; // conditions under which MyRange specialization is a view

This will restore the current behavior for all uses of MyRange in combination with range facilities.
